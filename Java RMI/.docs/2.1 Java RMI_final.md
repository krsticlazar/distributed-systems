# 2.1 Java RMI - finalno objasnjenje

Ovaj fajl spaja prezentaciju `2.1 Java RMI.md`, tvoje beleske i ono sto je prakticno bitno za ispit. Fokus je na sablonu koji se ponavlja u svim zadacima sa racunskih vezbi.

## Najkraci mentalni model

Java RMI omogucava da jedna Java aplikacija pozove metodu objekta koji zivi u drugoj JVM. Klijent ne dobija pravi serverski objekat, nego dobija stub, odnosno lokalni proxy koji implementira isti `Remote` interfejs. Server cuva pravi objekat, a `rmiregistry` samo povezuje ime objekta sa remote referencom.

Za ispit je najbitnije da umes da nacrtas i napises ovaj tok:

1. `Remote` interfejs opisuje metode koje smeju da se pozivaju udaljeno.
2. Implementacija nasledjuje `UnicastRemoteObject` i implementira taj interfejs.
3. `Server` napravi objekat i registruje ga preko `Naming.rebind`.
4. `Klijent` preko `Naming.lookup` dobije stub i poziva metode.
5. `Serializable` objekti se salju kao kopija, a `Remote` objekti kao udaljena referenca.

## Slajd 1 - Naslov

Tema prezentacije je RMI, odnosno Remote Method Invocation. Ovo je Java mehanizam za udaljene pozive metoda.

Za ispit: RMI nije nova mreza i nije baza podataka. To je nacin da poziv metode izgleda slicno obicnom OOP pozivu, iako se stvarno desava komunikacija izmedju procesa.

## Slajd 2 - Remote Method Invocation

Slajd uvodi skracenicu RMI. Bitno je da odmah povezes ime sa idejom: udaljeni objekat ima metode, a klijent ih poziva kao da radi nad lokalnim objektom.

Detalj iz beleski: iza toga postoje stub i skeleton mehanizam. Ti ih ne pises rucno, ali moras da razumes da stub pakuje poziv, argumente i identitet udaljenog objekta.

## Slajd 3 - Sta Java RMI omogucava

RMI omogucava poziv metode objekta koji se nalazi u drugoj JVM. Ta druga JVM moze biti na istom racunaru ili na udaljenom racunaru.

Svaka JVM ima svoj adresni prostor. Zato klijent ne moze direktno da uzme objekat iz memorije servera. Mora da koristi RMI mehanizam.

Za ispit: ako se kaze "klijent poziva metodu servera", tacnije je reci da klijent poziva metodu nad stub-om, a RMI sistem taj poziv prenosi do remote objekta.

## Slajd 4 - RMI kao objektno orijentisani RPC

RPC je udaljeni poziv procedure. RMI je slicna ideja, ali za Java objekte i metode. Zato se kaze da RMI obezbedjuje objektno-orijentisani RPC.

Na ovom slajdu je bitno razlikovati:

- poziv udaljene metode;
- prosledjivanje argumenata;
- vracanje rezultata;
- evoluciju od RPC-a do CORBA-e i RMI-a.

Za ispit: ne komplikuj sa CORBA detaljima. Dovoljno je da znas da je RMI Java-specific resenje za udaljene objekte.

## Slajd 5 - Procesi ucesnici

Tri glavna ucesnika su:

- klijent;
- server;
- registar objekata, odnosno `rmiregistry`.

Klijent poziva metode. Server sadrzi remote objekat. Registry povezuje simbolicko ime sa udaljenom referencom.

Dopuna iz beleski: klijent ne treba da zna ID svakog remote objekta rucno. Zato postoji registry. Server prijavi objekat pod imenom, a klijent trazi to ime.

## Slajd 6 - URL ime remote objekta

URL format je:

```text
rmi://hostname:port/name
```

Primer:

```text
rmi://localhost:1099/Kviz
```

`hostname` i `port` pokazuju gde je registry. `name` je ime pod kojim je server registrovao objekat.

Za ispit: port `1099` je najcesce port registra, ne mora biti port na kome stvarni remote objekat prima pozive. Remote objekat dobija svoj port pri export-u.

## Slajd 7 - RMI interfejsi i klase

Osnovni elementi su:

- remote interfejs;
- stub i skeleton;
- remote klasa, odnosno remote objekat.

Ovo je osnova skoro svakog zadatka. Kada vidis tekst zadatka, prvo izvuci remote interfejse i obicne serializable klase.

## Slajd 8 - Remote interfejs

Remote interfejs specificira metode koje klijent sme da poziva udaljeno.

Mora da nasledjuje `java.rmi.Remote`, a svaka remote metoda treba da baca `RemoteException`.

Tipican sablon:

```java
import java.rmi.*;

public interface Servis extends Remote {
    public void metoda() throws RemoteException;
}
```

Za ispit: ako metoda nije u remote interfejsu, klijent je ne moze udaljeno pozvati, cak i ako postoji u implementacionoj klasi.

## Slajd 9 - Klijent stub

Stub je proxy objekat u adresnom prostoru klijenta. Klijent poziva stub lokalno, a stub vodi racuna o komunikaciji sa serverom.

Bitno: stub implementira isti remote interfejs. Zato klijent promenljivu deklarise kao interfejs:

```java
Servis servis = (Servis) Naming.lookup("rmi://localhost:1099/Servis");
```

Za ispit: ne pisati `ServisImpl servis = ...` na klijentu. Klijent radi preko interfejsa.

## Slajd 10 - Sta stub radi

Stub:

- pravi konekciju ka remote objektu;
- pakuje argumente;
- salje zahtev;
- prima rezultat;
- raspakuje rezultat.

Marshalling znaci pakovanje podataka za slanje kroz mrezu. Unmarshalling znaci raspakivanje primljenih podataka.

## Slajd 11 - Server skeleton

Skeleton je serverski deo koji prima poziv, raspakuje argumente i poziva pravi metod na pravom remote objektu.

U modernoj Javi ga ne generises rucno, ali konceptualno postoji.

Dopuna iz beleski: ako server ima vise objekata, skeleton/RMI runtime zna koji objekat treba da primi poziv preko remote reference koju je klijent dobio.

## Slajd 12 - Remote klasa

Remote klasa implementira remote interfejs. Njena instanca postaje remote objekat kada se export-uje.

U studentskim zadacima najcesci sablon je:

```java
import java.rmi.*;
import java.rmi.server.*;

public class ServisImpl extends UnicastRemoteObject implements Servis {
    public ServisImpl() throws RemoteException {
        super();
    }
}
```

Za ispit: `UnicastRemoteObject` je praktican nacin da objekat postane dostupan za udaljene pozive.

## Slajd 13 - Arhitektura RMI sistema

Slajd nabraja sve delove RMI aplikacije:

- remote interfejs;
- implementacija;
- stub/skeleton;
- server;
- naming servis;
- klijent.

Za lab i ispit najcesce pises samo interfejse, implementacije, server i klijent. Stub/skeleton se ne pisu rucno.

## Slajd 14 - Koraci u razvoju RMI aplikacije, deo 1

Prvi korak je definisanje remote interfejsa.

Pravila:

- interfejs `extends Remote`;
- metode bacaju `RemoteException`;
- parametri i povratne vrednosti moraju biti primitivni tipovi, `Serializable`, ili `Remote` tipovi.

Za ispit: ovo je najcesce mesto gde se gubi poen u kodu. Ako vracas objekat obicne klase, ta klasa mora da implementira `Serializable`, osim ako je taj objekat remote.

## Slajd 15 - Koraci u razvoju RMI aplikacije, deo 2

Drugi korak je implementacija remote interfejsa i server.

Implementacija:

- nasledjuje `UnicastRemoteObject`;
- implementira sve metode interfejsa;
- konstruktor baca `RemoteException`.

Server:

- pravi implementacioni objekat;
- kreira ili koristi registry;
- registruje objekat.

## Slajd 16 - Koraci u razvoju RMI aplikacije, deo 3

Klijent:

- radi `Naming.lookup`;
- kastuje rezultat na remote interfejs;
- poziva udaljene metode.

Tipican kod:

```java
Servis servis = (Servis) Naming.lookup("rmi://localhost:1099/Servis");
servis.metoda();
```

Za ispit: klijent ne pravi `new ServisImpl()`. To bi bio lokalni objekat, ne RMI poziv.

## Slajd 17 - Kreiranje remote interfejsa

Primer sa `Calculator` pokazuje minimalan interfejs:

```java
public interface Calculator extends java.rmi.Remote {
    public long add(long a, long b) throws java.rmi.RemoteException;
}
```

Na ispitu mozes skraceno pisati `import java.rmi.*;`, pa onda:

```java
public interface Calculator extends Remote {
    public long add(long a, long b) throws RemoteException;
}
```

## Slajd 18 - Implementacija remote interfejsa

Implementaciona klasa zivi na serveru. Ona cuva stanje i izvrsava poslovnu logiku.

Ako ima metode koje nisu u remote interfejsu, one su lokalne pomocne metode i klijent ih ne vidi.

Za ispit: dovoljno je napisati konstruktor, polja i trazene metode. Validaciju i dodatne helper-e pisi samo ako zadatak trazi ili ako kratko pomaze demonstraciji.

## Slajd 19 - Stub i skeleton generisanje

Stare Java verzije su koristile `rmic`. U novijim verzijama stub se obezbedjuje dinamicki, pa se u laboratorijskim primerima `rmic` uglavnom ne koristi.

Za ispit: ako se pita teorija, kazes da stub/skeleton koncept postoji, ali ih u savremenom kodu najcesce ne generises rucno.

## Slajd 20 - Host server

Server kreira remote objekat i registruje ga u registry.

Najcesci sablon iz vezbi:

```java
LocateRegistry.createRegistry(1099);
Servis s = new ServisImpl();
Naming.rebind("rmi://localhost:1099/Servis", s);
```

Dopuna: `rebind` je zgodan jer pregazi staru registraciju pod istim imenom.

## Slajd 21 - Object name

Object name je URL:

```text
rmi://computerName:port/objectName
```

Ako se izostavi host i port, podrazumevaju se `localhost` i `1099`, ali na ispitu je cistije pisati pun oblik.

Za ispit: ime u `rebind` i ime u `lookup` moraju se poklopiti.

## Slajd 22 - Primer servera

Primer pokazuje:

```java
Calculator c = new CalculatorImpl();
Naming.rebind("rmi://localhost:1099/CalculatorService", c);
```

Ovo je ceo smisao serverske klase. Sve ostalo je samo hvatanje izuzetaka i zadrzavanje procesa zivim.

U vezbama se cesto dodaje:

```java
System.in.read();
```

da server ne zavrsi odmah.

## Slajd 23 - Klijent

Klijent mora znati:

- gde je registry;
- na kom je portu;
- pod kojim imenom je objekat registrovan.

Zatim radi:

```java
Calculator c = (Calculator) Naming.lookup("rmi://localhost:1099/CalculatorService");
```

Za ispit: rezultat `lookup` je stub, ali ga koristis kroz remote interfejs.

## Slajd 24 - Tipovi klasa u RMI

Postoje dve vazne grupe:

- remote klase;
- serializable klase.

Remote klasa ostaje na serveru i klijent dobija referencu/stub. Serializable klasa se kopira iz jedne JVM u drugu.

Primer: u zadatku eBanka `Korisnik` je remote, a `Stanje` je serializable snapshot.

## Slajd 25 - Prenos parametara

Ovo je jedna od najbitnijih stvari:

- primitivni tipovi se prenose po vrednosti;
- `Serializable` objekti se prenose po vrednosti;
- `Remote` objekti se prenose po referenci.

Za ispit: ako klijent dobije serializable objekat i promeni ga lokalno, server se ne menja. Ako klijent dobije remote objekat, njegove metode menjaju serversko stanje.

## Slajd 26 - Primeri

Ovo uvodi prakticne zadatke. Svi primeri iz `.zips` rade po istom sablonu:

- `CalculatorAcc` kao remote interfejs;
- `CalculatorAccImpl` kao remote implementacija;
- `Server` registruje objekat;
- `Client` radi `lookup`.

## Slajd 27 - Kraj prezentacije

Zakljucak za ispit: ne treba da pises infrastrukturu RMI-ja, vec da pravilno izdvojis remote interfejse, serializable objekte, implementacije, server i klijent.

## Minimalan sablon za ispit

```java
import java.rmi.*;

public interface Servis extends Remote {
    public void metoda() throws RemoteException;
}
```

```java
import java.rmi.*;
import java.rmi.server.*;

public class ServisImpl extends UnicastRemoteObject implements Servis {
    public ServisImpl() throws RemoteException {
        super();
    }

    public void metoda() throws RemoteException {
    }
}
```

```java
import java.rmi.*;
import java.rmi.registry.*;

public class Server {
    public static void main(String[] args) {
        try {
            LocateRegistry.createRegistry(1099);
            Servis s = new ServisImpl();
            Naming.rebind("rmi://localhost:1099/Servis", s);
            System.in.read();
        } catch (Exception e) {
        }
    }
}
```

```java
import java.rmi.*;

public class Klijent {
    public static void main(String[] args) {
        try {
            Servis s = (Servis) Naming.lookup("rmi://localhost:1099/Servis");
            s.metoda();
        } catch (Exception e) {
        }
    }
}
```
